## 14.08.2026 — доступ к базе: сетевая политика окружения и разделение строк

**Симптом.** Подключение к Neon не проходило ни по TCP на 5432, ни по HTTPS —
шлюз отвечал `403` на CONNECT для `*.c-2.eu-central-1.aws.neon.tech`.

**Причина.** Не строка подключения и не пароль, а сетевая политика cloud
environment: уровень **Trusted** пропускает только пакетные реестры и GitHub.

**Решение.** Уровень **Custom**, в `Allowed domains` добавлен `*.neon.tech`,
галочка «Also include default list of common package managers» оставлена — без
неё отвалились бы npm и GitHub.

**Как подключаться из контейнера.** Только SQL по HTTPS-эндпоинту Neon, пакет
`@neondatabase/serverless`. Обычный TCP-клиент не работает: прокси обслуживает
HTTPS, а не произвольные порты. Запускать с `NODE_USE_ENV_PROXY=1`, иначе
встроенный fetch Node 22 не читает `HTTPS_PROXY` и падает с `TypeError: fetch failed`.

**Две строки под разными именами.** `DATABASE_URL` — ветка разработчика,
`DATABASE_URL_PROD` — прод. Прод намеренно не в `DATABASE_URL`: эту переменную
подхватывает любая команда Prisma, и случайный `migrate` или `db push` ушёл бы
в боевую базу. Прод используется явно и только на чтение.

## 10.08.2026 — автораспределение плеч: принятые решения

**Перевозчик — реквизит направления, без версионности.** Одно направление везёт
один перевозчик. Историчность не нужна: у `Trip` собственное поле `carrierId`,
значение копируется при создании рейса, поэтому смена перевозчика в справочнике
не переписывает уже созданные рейсы. Версионность была бы обременением без выгоды.

**Ротация подрядчиков — в задачи на будущее.** Сегодня такого нет. Возможны
случаи, когда подрядчик меняется по графику; ежедневная ротация не рассматривается
вовсе — там проще создать рейс руками.

**Дробление одного плеча между машинами не делаем.** Заявка никогда не бывает
больше 33 паллет, поэтому ограничение схемы (`RequestCargoLeg.tripCargoUnitId`
уникален, связь 1:1) задачу не блокирует. Машины набиваем целыми плечами.
Это отменило запланированную миграцию и заметно сократило первый этап.

**Вместимость берём реальную, а не справочную.** У Трансхолода в справочнике
18 паллет, на Пятёрочку НН фактически грузят 20–22. Если алгоритм посчитает по
18, он закажет две машины там, где ездит одна. Причина расхождения не выяснена
(меньшие паллеты, второй ярус или заниженный норматив) — выяснить до реализации.

**Режим направления: «одна машина» против «дробить».** Пятёрочка НН — всё в одну
машину, пусть и с перебором. Казань — 50–60 паллет в сутки, это две фуры, а по
пятницам меньше 33 и хватает одной. Значит нужен явный признак режима, а не
универсальное правило.

**Шаблоны рейсов крепим к направлениям.** Идея пользователя, принята к
проработке. Тогда перевозчик, тип ТС и вместимость живут в шаблоне, а не
дублируются полями на направлении — один источник вместо двух, которые разъедутся.

**Ловушка, найденная при разборе:** `TripTemplate` в шаблон рейса остановки
маршрута НЕ сохраняет — в `operations/trips/page.tsx` и при сохранении, и при
применении стоит `routeStops: []`. Сегодня шаблон хранит только шапку рейса.
Чтобы шаблон задавал маршрут, эту логику придётся менять.

## 10.08.2026 — отчёты по данным отдаём в чат, а не строим в интерфейсе

**Решение.** Разовый аналитический запрос («сколько незаполненных объёмов за
неделю») выполняется и отдаётся цифрами в переписку. Постоянную страницу в
системе под это не заводим.

**Причина.** На запрос об отчёте была построена страница «Незаполненные объёмы»
с разделом в меню планирования (коммит `65187a7`, откачен). Пользователь отверг:
это лишняя нагрузка на систему, лишние данные и кнопки в интерфейсе ради разовой
задачи. Отчёт как функциональность заводим, только если он нужен регулярно и об
этом попросили явно.

## 10.08.2026 — GitHub: нужна установка приложения, а не только авторизация

**Симптом.** Чтение репозитория работало, любая запись отбивалась с
`403 Resource not accessible by integration` — и `git push`, и Contents API, и
создание ветки через Git Refs API.

**Причина.** Приложение Claude было **авторизовано** на аккаунтах (вкладка
Authorized GitHub Apps), но нигде не **установлено** (вкладка Installed пуста).
Авторизация даёт действовать от имени пользователя, доступ к репозиториям выдаёт
только установка.

**Что не является причиной** — на это ушло полдня, поэтому фиксирую: не роль
пользователя в репозитории (у `bald-logist` право `Write` было, он мёржил PR
#17–#22), не «отсутствие проекта на новом компьютере» (сессия работает в
облачном контейнере со своим клоном), не токен `gh` на локальной машине
(`gh` в контейнере не установлен вовсе, локальная машина в цепочке не участвует).

**Решение.** Владелец репозитория ставит приложение: страница приложения Claude
→ Install → аккаунт-владелец → Only select repositories → нужный репозиторий.
Проверка — приложение появилось на вкладке **Installed GitHub Apps**.

## 06.08.2026 — память хранится в git, не в Google Drive

**Решение.** Рабочая память ведётся в этой папке и коммитится в репозиторий.
Google Drive для этого не используется.

**Причина.** Claude Code подхватывает память автоматически только из файловой
системы — из `CLAUDE.md` и подключённых к нему через `@` файлов. Из Drive
автозагрузки нет: каждую сессию пришлось бы отдельно просить сходить в папку,
и один раз забыв — работать без контекста. Плюс в Drive нет версионирования и
связи записи с коммитом кода. Репозиторий уже лежит на GitHub и пережил потерю
ноутбука — этого достаточно, отдельное облако проблему не решает.

**Следствие.** Секретам в папке памяти места нет: `DATABASE_URL`, пароли,
токены, содержимое `.env`. Иначе папку придётся исключить из git — и она
повторит судьбу `SESSION_CONTEXT.txt`.
