## 22. Счета: логика расчёта стоимости на основе типов тарифов
Текущая логика счётов не учитывает тип тарифа. Нужно реализовать расчёт суммы счёта:
- Тип A (за паллет): кол-во паллет × ставка
- Тип B (скомпилированный): рейсовая ставка ÷ паллет_всего × паллет_клиента
- Тип C (ступенчатый): выбор ставки по порогу паллет
- Тип D (ставка + фикс): паллеты × ставка + фикс
- Дополнительные услуги: суммируются сверху
Итог: система сама считает сумму счёта при его создании.

### Поле «Кол-во паллет» в шапке заявки выглядит редактируемым, но не является им

Источник истины по объёму — грузы. В `pricing.ts` (`recomputeRequestFinals`)
количество в шапке при каждом пересчёте перезаписывается суммой по грузам:

```
// Кол-во паллет в шапке = сумма по грузам (грузы — источник истины).
```

При этом в форме заявки поле `requestedPallets` доступно для ввода
(`requests/page.tsx`). Если оператор поправит только его, `updateRequest`
сохранит значение и тут же вызовет пересчёт, который вернёт старое число.
Со стороны это выглядит как «система не сохранила правку».

Варианты: сделать поле только для чтения, когда у заявки есть грузы, либо
переносить введённое значение в единственный груз. Первое честнее.

### Планирование и портянка читают объём из разных полей

Сетка планирования показывает `CustomerRequest.requestedPallets`, портянка
берёт `RequestCargo.pallets`. Пока правки идут через груз, значения совпадают —
их синхронизирует пересчёт. Но это две разные точки чтения одного числа, и при
любом сбое синхронизации в сетке будет одно значение, а подрядчику уедет другое.
Привести к одному источнику.

### Версионность тарифов держится на одной дате и легко ломается

`validTo` не заполнен **ни у одного** тарифа перевозчика — 0 из 125. Версия
выражена только через `validFrom`: действующим считается весь набор строк с самой
поздней датой внутри ключа (направление либо пара точек), предыдущие даты —
история. Так группирует карточка договора (`carrier-contracts/[id]/page.tsx`,
`dateGroups[0] = актуальный`).

Отсюда две проблемы.

**Дата служит одновременно версией и датой начала.** Поэтому все строки одной
версии обязаны иметь **побитово одинаковый** `validFrom`. При вставке с `now()`
метки отличаются на миллисекунды, набор рассыпается на версии по одной машине, и
действующей остаётся последняя вставленная. Наступил на это 17.08, заводя тарифы
на Волгоград: из трёх машин осталась одна, три паллеты поехали за 100 000 вместо
76 190. Лечится приведением к дате без времени, но сама модель этого не защищает.

**Закрытый тариф выглядит действующим.** У Трансхолода VT-20 есть только в версии
от 01.03, версия от 20.06 его не содержит — то есть машина закрыта. Но `validTo`
у строки пуст, и любой запрос вида «validFrom <= сегодня и (validTo пусто или
validTo >= сегодня)» её вернёт. На этом ошибся автопланирование, пока не начало
отбирать версии как карточка.

Что стоит сделать: либо заполнять `validTo` при создании новой версии, либо ввести
явный номер версии, либо запретить хранить время в `validFrom` на уровне БД.
До тех пор любой новый код, читающий тарифы, обязан повторять логику карточки —
и это ровно тот случай, когда логику надо вынести в одну функцию, а не копировать.
